# Tracker：状态、联系、申请与时间（M45）

## 当前字段表示什么

| 数据 | 来源 | 可以说明什么 |
| --- | --- | --- |
| `interaction_type` | 用户选状态，或确认联系/申请时建立、推进摘要 | 当前跟进状态；不单独证明某封邮件已发送 |
| `updated_at` | 状态、备注、提醒等记录修改 | 这条记录最后更新时间；不能当作联系或状态发生时间 |
| `last_contacted_at` | 用户点击“我已发送”后的服务端确认 | 最近一次联系确认的时间；精确重试不刷新；不是从邮箱核实的实际发送时间 |
| `contact_events.actual_sent_at` | 用户选填的实际发送时间 | 用户自述；未知时为空，不从确认时间推断 |
| `contact_events.confirmed_at` | 保存新联系事件时的数据库时间 | 系统收到了用户确认，不证明邮件已送达 |
| `application_events.actual_submitted_at` | 用户选填的实际提交时间 | 未知时为空，不从确认时间推断 |
| `application_events.confirmed_at` | 保存新申请事件时的数据库时间 | 系统收到了用户确认，不证明申请已受理 |
| `material_artifacts.archived_at` | 实际 PDF 归档完成 | 文件保存时间，不是提交时间 |
| `application_material_records.recorded_at` | 用户补记材料的数据库时间 | 该文件后来关联到这次申请，不证明学校收到 |
| `interaction_status_changes.changed_at` | 数据库状态变化记录 | 本次状态写入时间；不能当作邮件送达或教授回复原始时间 |
| 邮件背景 `sent_on` | 用户填写前信日期 | 本次跟进写作的已确认背景；不自动修改 Tracker |

## 页面规则

- 切换状态保留已有联系日期。没有日期时继续留空，不生成“现在”。备注、提醒和重试也不能补写联系日期。
- 状态历史使用实际返回的变化记录。只知道当前状态时显示当前状态，不从 `updated_at` 推出“刚刚已回复”。
- 加载中、成功但没有历史、读取失败分别显示；失败可重试。没有配置存储或身份未就绪不能当作成功空列表。
- 机会或账号变化后，旧读取结果不进入新页面。数据库读取仍按当前身份和机会过滤。
- 生成、精修、复制、打开邮箱和设置提醒不确认发送。确认成功才更新联系摘要；已有已回复、面试、拒绝等状态保留。
- 明确重新生成草稿后，旧稿的确认失败不显示在新稿上。旧稿成功保存的真实联系摘要仍传回父页面，新稿需要另行确认。
- 复制成功或失败提示只对应实际复制的正文版本；重建、手写或AI替换后不能沿用旧提示。延迟返回的复制结果也不能标记另一份正文。
- 确认保存失败只说明没有拿到成功结果，不能证明没有写入。提示用户先查看 Tracker，再决定是否重试。

## 逐封联系记录（本地候选）

- 点击确认保存独立事件：目标、收件人、主题、完整正文、来源版本、可选实际发送时间及系统确认时间。历史页显示原文，不被后来精修覆盖。
- 来源版本是生成或精修该稿时的个人资料、目标及邮件背景摘要；保留旧稿时不会替换成新资料版本。手写修改保留原稿来源引用，但不声称全部文字均由AI生成或已核实。
- 版本引用不能恢复原始简历、PDF附件或历史资料全文。本批只保存邮件全文及来源版本引用，不声明附件已附上或送达。
- 相同目标、精确收件人/主题/正文及实际发送时间产生相同事件编号。编号不含账号，数据库以账号和编号共同确定记录；换设备或账号合并后的重试可复用。实际再次发送相同正文时需提供不同发送时间，否则按原记录处理。
- 同编号同内容返回原事件，不改确认时间、备注、提醒或当前状态。若来源版本或其他内容冲突，显示冲突，不新增记录或退回旧接口。
- 删除追踪摘要后原联系事件仍可在详情查看；重试旧事件不会重建已删除摘要。删除账号时清除该账号的邮件记录。
- 新事件和跟进摘要在同一数据库事务保存。已有已回复、面试、拒绝等状态不倒退。旧客户端的摘要确认接口保留兼容，但不会补造不存在的历史邮件。
- 浏览器只能读取本人事件，不能直接插入、更改或删除快照。账号合并通过已验证的Flow B流程移动归属，保留原文和时间；两边存在相同事件编号时整次合并回滚，不猜测或覆盖。
- 历史列表按时间与事件编号分页；首次加载失败和后续页失败可分别重试。换账号、换机会或刷新后，旧请求不能覆盖新页面。

## 正式申请记录（本地候选）

- “记录已提交申请”是独立入口，用户确认后才保存。打开申请网站、导出材料、生成邮件、选择 Applied 状态均不建立申请事件；已经关闭的目标也可记录过去的个人申请。
- 保存目标、提交渠道（网页表单、邮箱、其他）、实际提交位置、选填的提交时间、备注、当时已知的结果和下一步。实际时间未知时为空，系统确认时间单独保存；结果和备注是用户自述，不能证明对方收到、接受或回复。
- 不自动绑定当前简历，不将版本引用当作实际附件。用户可后来选择实际提交的 PDF，保存独立原文件和关联编号；简历历史重编号不影响已保存文件。
- 每次明确记录的新申请使用独立 UUID；同一次保存重试保留 UUID 和全部原文。真实重复申请即使时间未知、内容相同，也可在上一条保存成功后通过“记录另一次申请”建立新记录。
- 发起请求前，将原始记录保存在当前账号的私密浏览器存储中。刷新或关闭表单后可以恢复；结果未知时冻结原内容，支持查证和精确重试，不自动生成新编号。存储不可用时不发送保存请求。
- 同一浏览器的标签页通过 Web Lock 协调未决申请：相同内容复用，不同内容提示处理已有记录。记录按账号隔离，换号会清理本机私密草稿。另一设备不能仅凭相同内容推断同一次申请，必须先查看云端历史；不声称跨设备自动识别重复提交。
- 申请事件和摘要在同一事务保存。新摘要为 Applied；仅 Contacted 可前进到 Applied，回复、面试、拒绝等既有状态不倒退。联系时间、追踪备注与提醒保留；不会生成邮件事件。
- 相同编号的精确重试返回原事件和当前摘要，保留确认时间；删除摘要后不会重建。申请历史独立于邮件历史刷新，旧账号、旧目标和旧请求不能覆盖当前界面。
- 数据库只允许用户读取自己的事件，不能直接修改或删除事件。账号合并仅移动归属并保留原文与时间；编号冲突使整次合并回滚。删除账号会清除其申请记录。

## 实际申请 PDF（本地候选）

- 正式登录后，在单条申请历史补记当时实际提交的 PDF；明确确认后才归档和关联。原申请文字与时间保留。
- 每次一份 PDF，可再次添加独立文件；原字节下载，已归档文件不能被当前简历或同名文件覆盖。
- 上传未知时先核对；取消后永久撤销旧编号，允许换文件。删除先停止下载，再清理实际副本；失败可重试。
- 文件保留至用户删除文件或账号；未完成的暂存请求 24 小时后撤销并清理。
- 完整协议、大小上限及部署检查见 `material_archive_http_contract.md`。

## 部署顺序与验证范围

- 先在授权环境应用 `20260925095707_contact_event_ledger.sql` 、`20260925104726_application_event_ledger.sql` 及 `20260925115022_application_material_archive.sql`，再发布配套后端和前端。未部署迁移时确认报错，不回退到只保存摘要的旧接口。
- 事务与并发在本机临时 PostgreSQL 验证。材料另用真实本地 Auth、PostgREST 和 Storage 验证原字节、撤销登录、账号删除和物理清理。
- 正式材料源账号的合并使用本地预置授权后调用原合并接口，未验证完整浏览器合并流程。浏览器使用受控响应验证材料界面，两种证据分别保存。
- 托管数据库迁移、线上权限、真实邮件收发与用户验收未执行。
